# tflows 1.2 Technical Spec

## Overview

Version 1.2 focuses on reliability, better diagnostics, and a clearer extension model. The goal is to make the scripting engine safer, easier to maintain, and easier to extend without breaking existing 1.0/1.1 behavior.

This release is intentionally centered on four themes:

1. Validation and diagnostics
2. Safer plugin/module loading
3. Better scheduling and reliability
4. Observable runtime behavior

## Goals

- Catch invalid scripts before runtime when possible
- Improve error messages with exact file and line context
- Support a basic module/plugin model without introducing a heavy framework
- Improve scheduled task reliability through retries and timezone support
- Make runtime health and errors easier to inspect

## Non-goals

- Replacing the script engine with a Python-first framework
- Introducing a full app server or web dashboard in 1.2
- Breaking existing command syntax or backwards compatibility
- Creating a heavyweight dependency graph or package manager

## Target users

- Bot maintainers writing script-based commands
- Teams managing multiple scripts across guilds
- Developers who need clearer debugging and runtime visibility
- Power users building reusable script modules

## Functional requirements

### 1. Script validation and linting

The project should provide a validation pass that inspects a script before execution.

Requirements:
- `tflows check` should validate syntax and structure
- Undefined variables and function calls should be reported when probable
- Duplicate command names or conflicting registrations should be detected
- Commands with invalid trigger metadata should be rejected
- Validation should support both a single file and a directory of scripts

Example CLI behavior:

```bash
tflows checkmybot.py
tflows check ./scripts
```

Example diagnostics:

```text
script.flow:14:9: Undefined variable 'target_user'
script.flow:22:1: Unknown command 'warn' in local scope
script.flow:30:5: Function 'send_message' called before definition
```

### 2. Improved runtime errors

All runtime exceptions should include enough context to identify what script failed and where.

Requirements:
- Include script name, file path, command name, and line number where possible
- Include nested function traceback when a script function fails
- Include event and context metadata such as guild/channel when available
- Preserve human-readable error messages instead of leaking raw internals

Example error:

```text
Command failed: greet
  file: scripts/welcome.flow
  line: 12
  context: guild=123456789 channel=welcome
  error: cannot access field 'display' on null value
```

### 3. Module and plugin loading

The project should support a lightweight module model for reusable script code.

Requirements:
- Scripts can import other script modules from a configured root directory
- Relative imports are limited to approved script roots
- Duplicate imports are ignored safely
- Circular imports are detected and reported
- Module versions are surfaced in diagnostics

Design constraints:
- No arbitrary filesystem traversal outside the script root
- No remote imports or URL-based loading
- Non-script files are rejected

Example module API:

```py
from helpers.common import format_user
```

with an import root like:

```py
bot = FlowBot(prefix="!", script_root="./scripts")
```

### 4. Scheduler improvements

The scheduling system should be more robust and developer-friendly.

Requirements:
- Support timezone-aware jobs
- Accept timezone objects and IANA timezone names
- Support a retry policy for failed jobs
- Support natural-language or structured duration parsing for delays
- Prevent duplicate schedules with the same logical name unless explicitly replaced
- Allow a clean stop and restart lifecycle for all scheduled tasks

Example config:

```py
bot.schedule(
    name="nightly_cleanup",
    code="clean old invites",
    cron="0 3 * * *",
    timezone="UTC",
    retries=3,
    retry_delay="5m",
)
```

### 5. Observability and telemetry

The bot should expose enough runtime information to troubleshoot and monitor patterns in production.

Requirements:
- Track command execution counts
- Track command failures and error summaries
- Track scheduled task runs and failures
- Track basic latency metrics per command or event
- Allow logs to be emitted to a structured logger or debug output

Suggested output:

```text
[INFO] command=ping count=512 success=510 failures=2 avg_ms=18
[WARN] schedule=nightly_cleanup failed attempts=3 last_error=TimeoutError
```

## Technical design

### A. Validation pipeline

Introduce a validation phase that runs before dispatch and optionally via CLI.

Proposed flow:

1. Parse source into AST-like command tree
2. Walk command nodes
3. Collect symbol references
4. Resolve locals, globals, imported modules, and functions
5. Emit diagnostics with severity and location

Data model:

```py
@dataclass
class Diagnostic:
    severity: Literal["error", "warning", "info"]
    code: str
    message: str
    file: str
    line: int
    column: int
```

Validation categories:
- syntax error
- undefined symbol
- duplicate command registration
- invalid import
- invalid schedule config
- suspicious expression or dead code

### B. Error reporting layer

Introduce a consistent runtime error wrapper.

Proposed object:

```py
@dataclass
class FlowError:
    kind: str
    message: str
    file: str | None = None
    line: int | None = None
    command: str | None = None
    guild_id: int | None = None
    channel_id: int | None = None
    cause: Exception | None = None
```

Logging flow:
- command execution catches exceptions
- wraps them in `FlowError`
- writes to logger
- returns a human-safe failure message when needed

### C. Module loader

Add a lightweight `ModuleLoader` concept.

Responsibilities:
- resolve script roots and allowed directories
- read and parse module files
- detect duplicate imports and cycles
- expose exported functions/variables to the runtime

API sketch:

```py
class ModuleLoader:
    def __init__(self, root: str):
        ...

    def load_module(self, name: str) -> Module:
        ...

    def resolve(self, name: str) -> str:
        ...
```

Allowed patterns:
- modules loaded only from the configured `script_root`
- relative imports restricted to same root
- no `..`, no absolute paths, no remote URLs

### D. Scheduler reliability

The scheduling subsystem should become resilient and explicit.

Proposed fields:

```py
@dataclass
class ScheduleSpec:
    name: str
    code: str
    interval: str | None = None
    cron: str | None = None
    timezone: str | None = None
    run_once: bool = False
    retries: int = 0
    retry_delay: str = "5m"
```

Behavior:
- schedule names are unique by default
- replacing an existing schedule updates the old one cleanly
- retry attempts are spaced using the configured delay policy
- repeated failures are logged with final status

### E. Telemetry API

Add a lightweight runtime stats object.

Example:

```py
bot.get_runtime_stats()
# -> {
#    "commands": {"ping": {"count": 50, "avg_ms": 18, "errors": 1}},
#    "schedules": {"nightly_cleanup": {"runs": 10, "failures": 1}},
#    "uptime_seconds": 3600
# }
```

This should be read-only and not require external infrastructure.

## CLI requirements

### `tflows check`

Behavior:
- validates a script or directory
- exits 0 for valid scripts
- exits 1 for any diagnostic with severity `error`
- prints warnings separately from errors

Example:

```bash
tflows check scripts/main.flow
```

### `tflows stats`

Optional but likely useful for 1.2 if time allows:

```bash
tflows stats
```

Output:
- command counts
- error counts
- scheduled task snapshots
- uptime

## Backward compatibility

1.2 must not break 1.0 or 1.1 scripts.

Compatibility guarantees:
- existing command syntax remains valid
- previous prefix/slash behaviors remain supported
- existing state scopes are preserved
- current `bot.command`, `bot.schedule`, `bot.on_event` APIs remain valid

New validation should be additive and non-breaking by default.

## Acceptance criteria

### Must-have
- `tflows check` works on scripts and directories
- validation catches undefined names and invalid syntax
- import system supports allowed module loading with cycle detection
- schedule supports timezone and retry configuration
- runtime logging includes command, file, and error context
- all 1.0/1.1 tests still pass

### Nice-to-have
- `tflows stats` summarizes runtime behavior
- warnings are categorized by type and severity
- duplicate registrations emit clean validation errors
- schedule replacement lifecycle is deterministic and testable

## Testing plan

Add tests for:
- valid script passes validation
- undefined variable produces diagnostic
- duplicate commands are flagged
- circular imports fail clearly
- schedule retries are executed correctly
- timezone handling is consistent
- command errors include file and line context
- runtime stats are accurate

## Risks and mitigations

### Risk: validation is too strict and breaks valid scripts
Mitigation:
- treat many checks as warnings first
- allow opt-out for legacy compatibility paths

### Risk: module loading becomes security-sensitive
Mitigation:
- enforce script-root isolation
- never allow `..` or external network imports

### Risk: timezones create inconsistent behavior across systems
Mitigation:
- normalize all schedule times to timezone-aware datetimes
- test across UTC and local timezone scenarios

### Risk: telemetry adds overhead
Mitigation:
- keep metrics in memory and lightweight
- expose optional debug logging instead of forcing it on all bots

## Delivery plan

### Milestone 1: validation and diagnostics
- parser/walker improvements
- `tflows check` command
- better runtime error wrapper

### Milestone 2: module loader
- root-restricted import support
- cycle detection and duplicate handling

### Milestone 3: scheduler reliability
- timezone support
- retry policy
- stats and failure logging

### Milestone 4: observability
- metrics API
- debug output and summaries
- documentation and examples

## Summary

1.2 is primarily about making the framework easier to trust and easier to maintain. The biggest wins come from validation, better diagnostics, and a safe module model. The rest of the work should be incremental and additive so existing bots continue to work without migration pain.
